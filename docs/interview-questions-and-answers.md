> 状态口径：代码和本地验证已完成；真实模型、飞书、服务器部署、异地存储、并发长稳和真实业务 UAT 尚未完成。当前本地验证记录为构建通过、26 项自动化测试通过。不要把这些结果表述为真实模型准确率、生产可用性或客户使用效果。

## 阅读顺序与回答方法

先练习 Q1～Q10 的项目介绍和 Agent 定位，再掌握 Q11～Q30 的可信执行、检索和可靠性，最后准备权限、业务、测试及生产化追问。

每个回答按“结论 → 当前实现 → 取舍或不足”组织。首次回答控制在 30～90 秒，面试官追问后再展开代码细节。标为 P0 的问题应能脱稿回答；P1 用于深入追问。

## 核心术语速查

| 术语 | 在本项目中的含义 |
| --- | --- |
| SKU | 具体商品规格的唯一编码，例如 `AX-200`。Agent 从询价中抽取 SKU，再查询对应产品、MOQ、价格和知识文档。 |
| Message | 客户本次提交的原始询价，是后续核验与审计的原始事实。 |
| Agent Run | 一次询价处理的业务运行实例，记录运行状态、处理模式、结果摘要和关联报价。这里的 Run 不是程序进程。 |

## 一、项目介绍和业务价值

### Q1【P0】请用一分钟介绍你的项目。

**考察点：** 能否说清用户、业务问题、个人工作和技术价值。

**参考回答：**

我做的是一个面向外贸销售团队的客户经营与可信 Agent 协作平台。它覆盖客户询价、报价草稿、分级审批、人工交付登记、客户结果登记和订单履约。

核心难点是报价涉及成本、毛利和权限，不能直接相信模型的输出。我把大模型限制在询价结构化抽取，价格计算、权限校验、审批和状态转换由服务端执行。任务通过持久化 Worker 处理，客户偏好需要人工确认，报价绑定政策版本；知识证据还绑定文档版本和内容指纹。

当前完成了本地业务闭环、26 项自动化测试及部署和监控配置；真实外部账号联调与业务 UAT 还在待验收阶段。

**可能追问：** 你具体负责哪些模块？回答时只陈述实际参与和能解释的部分，不直接声称整套系统均由自己独立完成。

### Q2【P0】为什么做外贸 CRM？它解决了什么具体问题？

**参考回答：**

外贸询价通常以自然语言表达，SKU、数量、折扣和贸易地点可能混在一段话里；客户偏好又分散在不同会话中。同时，正式报价必须遵守成本底线和审批制度。

我选择这个场景，是因为它同时包含模型擅长的语言理解，以及必须由程序保证的金额、权限和流程约束，适合验证 Agent 如何安全地进入业务系统。当前主要验证技术闭环，尚没有真实销售效率提升或成交率数据。

### Q3【P0】相比普通 CRM 加一个聊天框，项目的区别是什么？

**参考回答：**

模型抽取结果通过 Schema、原文和业务规则校验后才会进入业务流程。系统继续检查产品、政策和缺失信息，生成可审批报价，并关联后续客户决定与订单。每次运行都有持久化任务、状态、工具记录和审计。

业务结果仍通过权限和规则校验才能落库。界面的聊天形式只是入口，主要设计工作在执行边界、恢复机制和审批一致性上。

### Q4【P0】你觉得最有代表性的三个技术点是什么？

**参考回答：**

**第一，可信执行边界。** 模型只负责询价字段抽取，金额计算、权限、状态转换和审批规则由服务端执行，正式报价必须经过人工审批。

**第二，持久化执行。** 接口在同一个数据库事务中写入客户原始 Message、一次处理对应的 Agent Run，以及供 Worker 领取的 Agent Job。任一步失败就整体回滚，避免“消息保存了但任务没创建”；Worker 再通过租约、重试和幂等约束处理中断与重复执行。

**第三，证据与版本治理。** 报价关联产品、政策、已确认偏好和有效知识；知识引用固化文档 ID、版本与 SHA-256 内容指纹，并在审批、发送和人工交付前复核。

这三个点分别应对模型误判、执行中断和业务依据变化。

### Q5【P0】项目已经上线了吗？有多少用户、QPS、准确率？

**参考回答：**

当前还没有正式上线，也没有真实用户规模、线上 QPS 或模型准确率数据。已有构建和 26 项自动化测试记录，并完成了生产 Compose、告警规则、压测及恢复演练脚本。

模型效果需要用标注询价集评测，容量需要在目标服务器测量，业务收益需要真实销售 UAT 和试运行数据支持。我不会把本地测试通过率当作模型准确率。

### Q6【P1】你说的参考架构是什么？其中技术全部实现了吗？

**参考回答：**

这里的参考架构是我最初借鉴的“跨境客户经营与智能协作平台”架构图，不是行业统一标准。它包含 WhatsApp 和飞书入口、MCP 工具网关、Mem0 客户记忆、WeKnora 企业知识、Pi Agent Core、Langfuse 观测以及 Docker Compose 部署等模块。

我没有做一比一复刻，而是实现了其中与可信报价最相关的思路：受控工具、组织与客户权限、人工审批、持久化 Worker、候选与确认记忆、知识证据版本治理和回归测试。我的前端是 React + Vite，后端是 Fastify，执行内核是确定性状态机，没有采用 Next.js 和 Pi Agent Core 通用循环。

Mem0、WeKnora、Langfuse 已提供可选适配器，但尚未用真实企业账号完成联调。飞书目前只用于内部通知，WhatsApp 自动收发没有接入；客户消息由销售录入，正式报价由销售通过原渠道发送后登记。因此我会区分“代码已实现”“适配器已预留”和“真实生产集成已验证”三个层次。

## 二、Agent 架构与模型边界

### Q7【P0】这算 Agent 吗？看起来更像固定 Workflow。

**参考回答：**

从执行结构看，它更准确地属于受约束的 Agent Workflow：模型理解非结构化询价，系统调用工具并根据结果决定补充信息、生成草稿或转人工，长期任务和人工审批状态都能持久化。

当前工具顺序由代码控制，模型没有自主规划或自由选择工具。我会明确这个边界。报价流程稳定且风险高，确定性编排更便于验证；后续可在低风险资料收集或跟进建议中引入受限规划。

### Q8【P0】为什么不用 ReAct、多 Agent 或现成编排框架？

**参考回答：**

当前任务路径清晰，主要是不确定的语言输入加确定的报价流程，暂时不需要多角色协商。自由循环会增加工具误用、延迟和成本，也让恢复与测试更复杂。

我先用状态机把业务边界实现清楚。未来复杂度提高时，可以引入支持检查点和人工中断的框架，但仍需由业务层实现幂等、权限和事务，框架本身不能替代这些约束。

### Q9【P0】一次询价从请求到完成是怎样执行的？

**参考回答：**

API 先检查身份、客户归属、CSRF 和幂等键，然后在一个事务中创建原始 Message、记录本次处理状态的 Agent Run，以及供 Worker 领取的 Agent Job，提交成功后返回 Run ID。Worker 领取 Job 后，读取产品、调用模型抽取，再查询客户、政策、记忆和知识。

字段缺失、低于 MOQ 或当前不支持的 CIF 场景会进入补充信息状态；模型失败则转人工复核。合法输入进入服务端计价，创建草稿和审批单。生产审批通过后等待人工交付登记，客户接受后再生成订单。

**代码定位：** [API](../server/index.ts)、[执行引擎](../server/engine.ts)。

### Q10【P0】大模型具体做了什么？哪些内容会发给模型？

**参考回答：**

当前模型只抽取 SKU、数量、折扣、贸易术语、指定地点和备注。输入是客户本次询价、允许的 SKU 列表和抽取指令，使用兼容 Chat Completions 的接口，要求 JSON 输出。

成本、毛利和审批决策没有交给模型，检索片段当前也没有拼入抽取提示词。模型调用有 15 秒超时，输出经过 JSON 解析、Zod Schema 和原文核验。

**代码定位：** [模型抽取](../server/model.ts)。

### Q11【P0】怎么防止模型幻觉？JSON 格式正确就可信吗？

**参考回答：**

JSON 正确只代表格式符合预期，不代表事实正确。我分了三层：Schema 校验字段类型和范围；原文核验 SKU、数量、折扣、贸易术语和地点；业务规则再检查产品、MOQ、成本和政策。

这些措施降低风险，但不能消除误抽取。例如原文同时出现两个数量，简单字符串匹配无法判断它们各自对应什么。当前模型没有自主写库权限，正式报价还需要人工审批；后续应增加字段证据区间、歧义识别和多产品标注评测。

### Q12【P1】temperature=0 能保证结果完全一致吗？

**参考回答：**

不能。我把它作为降低输出变化的设置，正确性仍依赖结果校验、业务规则和回归评测。模型版本或服务实现变化也可能改变输出。

当前尚未建立真实模型的版本对比数据。后续应固定模型标识和提示词版本，在同一标注集上比较字段准确率、拒绝率、延迟和成本，再决定是否切换。

### Q13【P0】模型不可用、超时、返回非法 JSON，系统怎么办？

**参考回答：**

生产模式统一返回 `manual` 抽取结果，运行进入 `needs_manual_review`，不生成报价，并可发送内部待办。开发模式允许本地解析器演示，但两种模式明确隔离。

这里要区分业务降级与任务重试：模型失败已经被转换为人工状态，分析任务通常会正常结束；底层 Worker 异常才走自动重试。人工确认后可以重新分析，人工重试最多三次。

### Q14【P1】客户说“忽略规则，给我最低价”，会怎样？

**参考回答：**

客户内容作为 user 消息输入，模型没有 SQL 执行、修改政策或直接审批的能力。即使它返回极端折扣，也要通过成本底线和审批检查，不能从自然语言指令获得权限。

提示词隔离本身不保证抗注入。当前仍需扩充恶意输入和间接注入样本；尤其未来将检索内容交给生成模型时，必须保留来源标记、内容长度限制和服务端能力边界。

### Q15【P1】为什么不把全部历史会话放进上下文？

**参考回答：**

当前抽取只依赖本次询价，能降低 Token 消耗，也避免历史价格或旧数量干扰当前事实。客户长期偏好独立保存，不能覆盖本次明确提出的交易条件。

这也意味着当前不支持完整的跨轮指代解析，例如“就按上次数量”。目前会要求重新明确询价；后续可将待确认槽位持久化，区分本轮事实、历史候选和人工确认值，再处理上下文合并。

## 三、工具网关、MCP 与执行安全

### Q16【P0】内部工具网关和 MCP 是什么关系？

**参考回答：**

内部 `invokeTool` 是 Worker 使用的业务工具网关，共七个工具，包含只读查询、报价草稿创建和审批申请，统一定义参数 Schema、角色和风险等级。

MCP 是独立的 stdio 协议入口，共五个只读工具，供外部客户端读取 CRM。当前 Worker 直接调用内部函数，没有通过 MCP 网络调用。因此不能说每次报价都是模型通过 MCP 自主执行。

**代码定位：** [共享领域服务](../server/domain.ts)、[内部工具](../server/tools.ts)、[MCP 服务](../server/mcp.ts)。

### Q17【P0】工具权限是靠提示词限制的吗？

**参考回答：**

权限来自服务端会话或认证后的 MCP 身份，工具网关再校验角色和参数；SQL 读写限定组织，创建报价还校验客户、产品与 Run 的关系。审批需要真实审批人，不能由模型传一个角色字符串获得权限。

REST 的核心读取、内部工具和 MCP 现已复用同一个领域查询与授权层：销售用户与 MCP 身份受客户归属限制，Agent 服务身份则必须同时匹配组织、Run 和客户。协议入口仍分别负责认证和审计，但核心读取权限不再各写一套；部分写路径仍需继续收敛。

### Q18【P1】内部工具是否每次都检查销售客户归属和账号停用？

**参考回答：**

HTTP 客户接口和 MCP 入口有对应检查，MCP 每次调用还会重新读取账号状态。但当前 Worker 用 `agent_worker` 服务身份执行，内部网关主要校验组织、角色和运行关联，并没有逐次重新核验原发起人的客户归属和账号状态。

这是一个待加强的边界。若客户移交或发起人停用后任务仍在排队，应明确业务策略，并在敏感步骤重新核验发起人授权或取消任务。不能把入口校验说成覆盖了所有执行时刻。

### Q19【P1】为什么 MCP 只开放读工具？MCP 本身能保证安全吗？

**参考回答：**

MCP 统一工具发现和调用格式，安全仍由服务端认证和授权实现。当前只开放客户及已确认偏好、产品、政策和知识读取，不暴露报价创建、审批或发送，缩小外部客户端的能力范围。

测试通过 MCP SDK 客户端验证握手、只读工具、租户和客户归属边界。当前使用本地 stdio 与环境凭据认证，尚没有远程传输及企业身份集成，不能据此声称完成远程 MCP 安全治理。

### Q20【P1】工具执行失败后，日志一定完整吗？

**参考回答：**

业务执行阶段的成功或异常会在 `finally` 中写入工具日志，生产模式只保存字段名和结果状态，避免复制客户原文和金额。

但角色和 Schema 校验位于当前 `try/finally` 之前，这类拒绝不会自动进入该工具日志；如果数据库不可写，日志也可能失败。后续需要统一安全事件入口、授权拒绝审计，以及独立日志通道，不能说所有失败都已完整持久化。

## 四、知识检索与客户记忆

### Q21【P0】你用了 RAG 吗？向量库、Embedding、Reranker 怎么做的？

**参考回答：**

当前本地知识检索先过滤租户、发布状态、有效期和产品范围，再按关键词命中排序，取前三条。可选 WeKnora 接口能返回外部片段；仓库没有自行实现 Embedding、向量库或面向知识文档的语义 Reranker。Mem0 记忆链路另有轻量重排，它组合关键词相关度和供应商分数，不应包装成完整向量 RAG。

检索结果当前用于证据展示和草稿证据引用，没有交给模型生成答案。因此我会把现阶段称为“知识检索与证据约束”，不会把完整向量 RAG 链路说成已经实现。

### Q22【P0】怎么避免引用过期文档或其他产品的手册？

**参考回答：**

本地查询要求文档已发布并且当前有效；指定 SKU 时，只允许该 SKU 的文档或通用文档。进入报价时，工具还会重新构造当前允许的证据 ID 集合，对输入证据做白名单过滤。

报价记录文档 ID、版本和 SHA-256 内容指纹，政策记录 ID 和版本。审批、发送和人工交付前都会重新检查知识发布状态、有效期、版本和正文指纹；即使没有升版本而静默修改正文，报价也会失效。外部 WeKnora 结果标记为 `unverified`，不会直接进入报价的权威证据集合。

### Q23【P1】本地检索有什么不足？如果升级，你会怎么做？

**参考回答：**

关键词命中无法很好处理同义词和语义相关性，当前取前三条时也没有最低相关性阈值，零命中内容仍可能返回。本地文档没有专门的切分和重排流程。

改进顺序是先建立“问题—相关文档”的标注集，再增加合理切分、混合召回、相关性阈值和重排。租户、权限、产品和版本过滤仍需保留在服务端，不能用语义相似度替代访问控制。

### Q24【P0】客户记忆与聊天历史、知识库分别有什么区别？

**参考回答：**

聊天历史记录客户说过什么；客户记忆保存长期偏好，例如包装或沟通习惯；企业知识保存组织发布的产品资料和政策。交易数量、当前折扣和价格不能因为历史中出现过就直接沿用。

当前显式偏好通过规则提取为 `candidate`，记录来源消息，人工确认后才成为 `confirmed`。这个过程没有使用模型自动生成复杂记忆，也没有实现自动冲突裁决。

### Q25【P0】Mem0 在你的系统里实际起什么作用？

**参考回答：**

它是可选的外部偏好同步和检索适配器，需要显式开启。人工确认偏好后才同步，外部隔离键使用 `organizationId:customerId`。检索结果标记为未核实线索，本地确认记忆仍是主要依据。

Mem0 请求最多 50 条候选，本地用组织/客户作用域、内容 Hash 去重和相关性重排后只注入 Top 10，返回前脱敏邮箱与电话。结果仍不驱动定价或审批；外部同步失败目前没有持久重试和删除同步，真实账号联调也尚未完成。

### Q26【P1】客户偏好冲突或变化后怎么办？

**参考回答：**

当前候选与确认状态分开，但还没有完整的“失效、替代、冲突”模型。人工确认也不代表事实永远有效，数值置信度更不是统计校准后的概率。

下一步会为偏好增加类型、有效期、确认人、替代关系和冲突状态；同类新旧偏好冲突时要求人工选择。付款账期等高风险内容应进入正式业务政策，不能仅作为自由文本偏好生效。

## 五、任务、事务与幂等

### Q27【P0】为什么要异步任务？请求里直接调模型不行吗？

**参考回答：**

模型调用可能持续十几秒，前端断开或请求超时不应该让业务任务丢失。我在同一事务中保存消息、Run 和 Job，提交成功后返回 202，Worker 再处理。

这让执行状态不依赖浏览器连接，也能支持租约、重试和人工审批。当前任务表与业务数据共用 SQLite，是单机阶段减少分布式一致性复杂度的选择。

### Q28【P0】怎么避免用户点两次，生成两份报价？

**参考回答：**

询价接口要求幂等键，数据库有组织与请求键的唯一索引。同一键且客户和正文相同，返回原 Run；同一键对应不同内容返回 409。

还设置了每个 Run 唯一报价、每个报价唯一审批、每种 Run 任务唯一等约束，代码重复执行时优先复用已有记录。不同幂等键的相同文本仍可能代表两次真实请求，因此不会简单按正文去重。

### Q29【P0】Worker 崩溃后，任务如何恢复？

**参考回答：**

领取任务在 `BEGIN IMMEDIATE` 事务中完成，写入租约所有者、30 秒到期时间和递增版本；运行时每 10 秒续租。进程中断后，过期运行任务可以再次领取。

执行后的更新带所有者和版本条件，关键步骤检查租约，防止旧执行者覆盖新任务状态。当前不是严格分布式执行保证：同步阻塞会影响续租，部分写入点仍需补租约校验和故障注入测试。

### Q30【P1】lease_version 和乐观锁有什么区别？

**参考回答：**

`lease_version` 标识本次任务领取代次，避免过期 Worker 提交旧执行结果；订单 `version` 标识业务记录版本，避免两个成员基于同一旧页面互相覆盖。

两者都利用条件更新，但保护对象不同。当前租约版本尚未传到每一处业务写入，属于局部 fencing 保护，不能宣称已经证明所有副作用在租约切换下严格安全。

### Q31【P0】自动重试和人工重试是怎么区分的？

**参考回答：**

任务异常默认最多尝试三次，退避按 `2^attempt` 秒计算并设上限。达到次数后任务失败，保留错误并生成待办。

模型不可用走业务降级，Run 等待人工复核，不进行无限模型重试。人工重试仅允许失败或人工复核且尚无报价的 Run，最多三次，并留下操作者审计。当前尚未实现按错误类型细分重试和抖动，属于可改进点。

### Q32【P0】你实现了 Exactly Once 吗？

**参考回答：**

我不会对外部系统承诺全局 Exactly Once。当前数据库范围内，用事务、唯一键和状态检查保证重复运行不重复生成关键记录；开发演示消息和 Outbox 也在同一数据库事务内去重。

真实客户渠道尚未自动接入。跨网络发送存在“对方已接收、本地未记录”的不确定窗口，需要供应商幂等键、状态查询、回执和对账。飞书超时目前进入 `uncertain`，由人工核对。

### Q33【P1】为什么用 SQLite？WAL 能解决什么，不能解决什么？

**参考回答：**

当前目标是单团队、单机部署。SQLite 让消息、任务和报价可共享本地事务，开发和恢复成本较低。配置了 WAL、外键和 5 秒 busy timeout。

WAL 有利于读写并行，但写事务仍会竞争；它不会自动带来多节点高可用。当前还使用同步 SQLite API，长查询、备份或密码计算可能阻塞事件循环。没有实际容量测试前，我不会给出可支持人数或 QPS 的承诺。

### Q34【P1】什么时候迁移 PostgreSQL 和消息队列？

**参考回答：**

当写锁等待、事件循环延迟、队列等待时间持续超标，或者业务要求多实例和自动恢复时，就需要迁移。判断依据应来自压测和恢复目标。

迁移 PostgreSQL 后可用事务和行级领取任务机制；如果再引入独立消息队列，应通过事务 Outbox 解决业务提交与消息发布的一致性。迁移还需要数据校验、备份、停写窗口和回滚方案，不能仅修改连接字符串。

## 六、报价、审批与外贸业务

### Q35【P0】为什么金额使用整数分？具体怎么算？

**参考回答：**

当前金额以最小货币单位保存，折扣和毛利用基点，10000 基点代表 100%。单价先按折扣计算并四舍五入，再乘数量得到总价；总价必须是安全整数。

示例 AX-200 标价 1280 分、成本 850 分，打八折后单价 1024 分，5000 件总价 5120000 分，毛利率约 16.99%。当前按分处理，还未完整覆盖不同币种精度、税费、汇率与财务舍入政策。

### Q36【P0】高折扣为什么要财务审批？规则是配置化的吗？

**参考回答：**

当前所有正式报价都要人工审批：折扣超过 1500 基点，或者毛利低于政策线，要求财务；其他情况要求经理。成本底线是硬拦截，不只是升级审批。

这里有一个具体局限：财务折扣阈值 15% 目前写在代码里，政策中的销售折扣上限用于审批原因说明，并不完全等同于财务路由阈值。后续应将阈值、审批人和规则版本统一配置，防止制度与实现偏离。

### Q37【P0】人工批准后，政策变化了，旧报价还能发吗？

**参考回答：**

报价绑定政策 ID、政策版本、报价版本、贸易地点和有效期；审批记录绑定报价版本，知识证据还保存文档版本与内容指纹。在审批、演示发送或人工交付登记前，服务端会重新检查。政策变化、知识撤回或静默修改、报价过期或条款不完整，都会使审批失效并标记报价陈旧。

当前重点验证了政策和报价版本；产品成本变更后的重审批策略尚未完整覆盖。后续需要产品版本或价格快照，并明确“价格冻结”与“重新计价”的业务规则。

### Q38【P0】怎么防止创建人自己审批？管理员能绕过吗？

**参考回答：**

审批函数读取 Run 的创建人，与当前审批人比较，相同就拒绝。管理员可以通过角色门禁，但同样需要通过创建人检查。

检查位于服务端审批函数内，和审批状态、版本校验一起处于事务中，因此绕过前端按钮也不能自批。对应自动化用例验证了创建人即使具备要求的角色也被拒绝。

### Q39【P0】FOB、EXW、CIF 为什么处理不同？

**参考回答：**

当前报价数据模型只支持自动生成 FOB、EXW，并要求询价明确写出指定地点。字段名 `destination` 在当前实现里承载这个地点，但它不一定是目的港，后续应统一命名为 `namedPlace`。

CIF 涉及当前系统未接入的物流费用等信息，因此要求补充与人工确认。支持 FOB、EXW 字段也不代表已实现完整贸易费用核算，当前仍是受限的单产品报价模型。

### Q40【P0】生产模式为什么是人工发送？怎么证明客户收到？

**参考回答：**

当前没有接入客户渠道的自动发送和回执接口，所以审批后进入 `manual_delivery_required`。销售在原渠道发送后登记渠道、外部凭据和说明，系统校验权限、有效期及凭据去重。

这个状态只表示人工发送已登记，不能证明客户送达或已读。客户接受也是销售依据外部回复登记，后续需要签名回调、供应商消息 ID 和对账机制来加强真实性。

### Q41【P0】报价转订单怎么保证数据一致和不重复？

**参考回答：**

只能对已交付的报价登记客户结果，接受时还必须在有效期内。客户结果、订单、订单事件和审计在一个事务中创建；每个报价最多一个客户结果和订单，外部凭据在组织与渠道范围内唯一。

订单复制获批报价的数量、币种、单价、总价和贸易条款，避免后续产品价格改变历史金额。预计出货时间当前仍使用产品现有交期计算，并未冻结完整交期快照；付款、质检和单证流程尚未实现。

### Q42【P1】多人同时改订单怎么办？能跳过生产直接完成吗？

**参考回答：**

更新接口要求提交 `expectedVersion`，SQL 更新条件包含当前版本，并将版本加一；冲突返回 409，让用户刷新。状态表控制合法转换，不能任意跳转。

风险状态要求说明，出货要求物流或提单编号，取消需要经理或管理员。当前是人工维护的履约流程，物流编号没有接第三方核验，取消也未关联库存、收款等补偿动作。

## 七、身份、权限与数据安全

### Q43【P0】多租户隔离怎么做？传另一个客户 ID 会怎样？

**参考回答：**

HTTP 请求的组织来自服务端会话，不相信客户端传来的组织。业务查询按组织过滤；销售还要通过负责人检查。不存在或无权访问的客户返回 404，减少资源枚举信息。

MCP 同样从认证用户取得组织并检查归属。REST 的客户、产品和生效政策读取、内部 Agent 工具与 MCP 已复用共享领域查询和授权层；销售按客户负责人过滤，Agent 服务身份按组织、Run 与客户绑定校验。数据库外键仍并非全部为复合租户外键，写路径也尚未全部收敛，因此还需用数据库约束和统一写服务继续减少遗漏风险。

### Q44【P0】有角色权限后，为什么还要客户归属和字段脱敏？

**参考回答：**

角色决定“可以做什么”，客户归属决定“对哪些客户可以做”。销售有读取客户的角色权限，但不能读取别人的客户。

字段级权限则解决“允许读取的记录中哪些内容可以看到”。销售返回数据会过滤成本、毛利和内部运行信息。当前接口和 MCP 仍有细节需要统一，例如 MCP 政策工具直接返回完整政策对象，应进一步评估敏感阈值是否需要隐藏。

### Q45【P0】为什么用 Cookie Session？如何防 CSRF？

**参考回答：**

当前是浏览器应用，数据库 Session 便于撤销和停用。会话令牌由随机字节生成，生产 Cookie 带 HttpOnly、Secure 和 SameSite=Lax，默认有效期八小时。

写接口除登录外需要 Session 和 `X-CSRF-Token`，服务端与会话中 Token 做比较。CSRF 校验保护写请求，但不能替代角色和对象权限检查；HTTPS 也需要真实部署后验证。

### Q46【P1】账号停用或密码改变后，旧连接还能访问吗？

**参考回答：**

HTTP 每次请求关联有效用户和会话，停用后旧会话不能继续访问；改密撤销其他会话。MCP 每次工具调用也重新读取账号活跃状态，能够感知停用。

但当前 MCP 只在进程启动时校验密码，因此改密不等于既有 MCP 进程自动失效，除非停用账号或增加凭据版本检查。异步 Worker 是否继续处理旧任务，也是需要单独定义的授权时效问题。

### Q47【P1】密码和密钥怎么保存？当前还有什么风险？

**参考回答：**

用户密码使用随机盐加 scrypt 派生保存，通过时序安全比较验证。模型和飞书等服务密钥支持独立文件读取，由 Compose Secret 挂载，生产监控要求至少 32 字符令牌。

文件型 Secret 仍需要主机文件权限和备份保护，不代表自动加密或完成轮换。当前同步 scrypt 也可能在登录压力下阻塞事件循环；后续可改为异步计算，并接入企业身份、MFA 和集中密钥托管。

### Q48【P1】模型、记忆和日志会泄露客户数据吗？

**参考回答：**

模型会收到本次询价，询价可能包含个人信息，因此不能说“没有数据出域”。开启 Mem0 后，确认偏好及检索查询也可能发往外部；WeKnora 会收到查询。

当前对飞书通知和 Langfuse 采用数据最小化：飞书只发待办类型和记录 ID，追踪只导出运行及工具元数据。客户原文仍保存在本地业务库，权限、保留期限、删除与外部账号的数据处理政策仍需验收。

## 八、测试、可观测性和生产化

### Q49【P0】26 项测试和 8 项 Golden Corpus 分别证明什么？

**参考回答：**

26 项是自动化测试用例，覆盖租户与权限、CSRF、幂等、报价规则、MCP、Mem0 重排与脱敏、知识指纹失效、生产降级、订单和备份恢复。Golden Corpus 是八个演示固定业务断言，包含本地解析、金额和知识状态等。

这些不等于标注真实模型数据集。部分 Golden Corpus 检查较粗，例如是否同时存在候选和确认记忆；更强的边界由其他测试补充。真实模型字段准确率、误报价率与业务收益尚未测量。

### Q50【P0】如果评测真实模型，你会设计哪些指标？

**参考回答：**

先构建覆盖语言、数量写法、缺失字段、否定、多个 SKU、历史指代和恶意指令的人工标注集，保留独立测试集。字段级测 SKU、数量、折扣、条款和地点的准确性，任务级测完整抽取正确率、错误放行率、漏拦截和人工复核率。

还要统计延迟 P50/P95/P99、超时率和单次成本；业务侧看销售修正比例及审批返工。不能只追求复核率低，否则可能牺牲错误拦截。

### Q51【P0】怎么证明能扛并发、稳定运行？你已经压测了吗？

**参考回答：**

目前提供了并发与最长 24 小时长稳脚本，但还没在目标环境执行，因此没有容量结论。脚本当前主要测询价接口返回 202 的延迟和状态，不能代表模型完成吞吐量或报价成功率。

完整测试还需跟踪提交到 Run 终态的耗时、队列等待和积压、Worker 完成速率、事件循环、内存与写锁。现有脚本把延迟保存在内存，长稳时也应改流式统计，并处理八小时会话过期与合成数据增长。

### Q52【P0】如何定位“接口正常但报价一直没出来”？

**参考回答：**

我会沿 Run ID 查状态、任务、事件和工具结果。先区分运行正在等待人工、缺失字段、模型降级，还是 Worker 没有领取任务；再查看心跳、租约、重试次数和队列积压。

生产 readiness 检查数据库与分离 Worker 心跳，Prometheus 还有失败任务和积压信号。但心跳正常不能证明业务持续进展，后续需要最老任务年龄、完成速率和合成探测，避免 Worker 活着却不消费。

### Q53【P1】日志、指标、Trace、审计各用来做什么？

**参考回答：**

日志用于故障细节，指标用于趋势和告警，Trace 用于关联一次运行的跨步骤执行，审计记录谁对业务数据做了什么。当前有 Run 事件、工具日志、业务审计、Prometheus 和可选 Langfuse 导出。

工具网关现在记录 `duration_ms`，Langfuse 工具 Span 使用实际开始时间和执行耗时，可以观察工具级延迟；生产模式仍只导出白名单元数据，不包含工具输入输出。当前还没有完整的模型 Token 与成本记录，数据库审计也不具备防篡改证明，后续应补模型 Usage 采集和独立审计存储。

### Q54【P0】告警链路有什么薄弱点？

**参考回答：**

当前 Prometheus 抓取内部指标，Alertmanager 将事件发回 API，再通过本系统的飞书通知队列发送。因此 API、数据库、通知进程或主机整体故障时，这条告警链可能同时失效，需要独立外部探测和第二通知通道。

另外，数据库异常会让指标请求失败，此时主要依靠 `up=0` 告警，健康值不一定能返回 0。告警当前使用固定去重键，重复触发和恢复通知生命周期也需要加强；已有配置不代表真实告警闭环已验证。

### Q55【P0】为什么不能直接复制 SQLite 文件备份？恢复演练做了什么？

**参考回答：**

WAL 模式下直接复制主文件可能遗漏日志中的已提交变更。我使用 `VACUUM INTO` 生成一致性快照，并对快照执行完整性检查。

恢复脚本把快照复制到临时目录，检查完整性、关键表、外键和记录数，自动化已执行。但它还没有完整启动恢复环境、验证登录和业务链路，更没有对真实异地快照测 RPO/RTO。后续需要把这些纳入演练证据。

### Q56【P1】RPO、RTO 怎么定？异地备份已经完成了吗？

**参考回答：**

RPO 衡量可接受的数据丢失时间范围，RTO 衡量可接受的恢复耗时，应由业务目标决定，再通过备份和演练证明。当前有 rclone 上传、校验配置，但没有真实异地上传下载和恢复时间数据。

备份计划还需要由服务器定时器或调度平台执行，当前辅助任务不是自动完成的备份 SLA。还要保护远端凭据、加密密钥、版本保留和恢复所需的配置文件，并定期抽查异地恢复。

### Q57【P0】现在可以直接交给外贸团队生产使用吗？

**参考回答：**

我把当前状态定义为代码和生产基础设施配置已完成、等待真实环境验收的候选版本。单机目标明确，但还没有真实服务器长稳、模型账号、飞书群、异地恢复和销售 UAT 的验收结果。

允许上线的业务范围也要明确，例如一期接受人工录入和人工交付、单产品报价、限定贸易条款。不能仅凭自动化通过就承诺生产平稳运行，更不能把未实现的收汇、质检或报关流程包含在交付范围。

## 九、压力追问、个人贡献和改进优先级

### Q58【P0】项目最难的问题是什么？你具体怎么解决的？

**参考回答：**

我认为最难的是把“一次正确输出”变成“一个持续可信的业务结果”。例如报价创建时合法，但审批期间政策更新，继续使用旧批准就会出现风险。

我把报价、政策和审批版本关联，知识引用再绑定文档版本和内容指纹，在审批、发送和交付前重新校验；同时为重复请求和重复执行设置唯一约束。这样系统关注的是业务不变量，而不仅是模型输出格式。这个回答应结合我能现场演示和解释的代码展开。

### Q59【P0】如果让你继续优化，前三件事是什么？

**参考回答：**

第一，建立真实脱敏询价标注集，补歧义、多产品和注入测试，明确错误放行率。第二，在现有共享领域授权层之上，补发起人停用或客户移交后的执行时授权检查，并让所有敏感写入遵守租约栅栏。第三，在隔离环境完成真实模型、飞书、恢复、长稳和 UAT，并让告警独立于应用主链路。

如果业务进一步需要多实例和高可用，再推进 PostgreSQL、可靠消息投递和迁移演练。优先级由实际风险和目标决定。

### Q60【P0】代码里有哪些你已经识别但尚未解决的问题？

**参考回答：**

主要有六类：抽取的原文子串校验不足以解决语义歧义；知识检索仍是关键词方案，Mem0 重排也只是轻量启发式；Worker 对发起人授权时效和租约保护尚未覆盖全部敏感写入；财务折扣阈值仍有硬编码；真实渠道回执和多产品/付款等业务不完整；告警、恢复和长稳尚缺外部实测。

我能把这些问题对应到具体代码与测试缺口，而不是把未来计划当作当前能力。项目的工程价值在于已经实现的边界及验证方法，剩余部分也需要清楚说明。

### Q61【P0】用了 AI 辅助开发，如何证明是你掌握的项目？

**参考回答：**

如果使用了 AI 辅助，我会如实说明。我的掌握程度应通过现场解释与修改来验证：讲清一次询价的数据流，解释为什么模型失败不能生成报价，说明政策变化后的状态，以及重复执行为何不会重复生成订单。

我会准备现场改一个阈值、增加一个失败测试，或定位一次错误运行。对尚不能解释的模块不夸大贡献，先理解其数据结构、约束和失败路径，再写到简历。

### Q62【P1】你的项目为什么用 Node.js？Agent 岗位不是常用 Python 吗？

**参考回答：**

当前模型调用主要是 HTTP 接口，业务重点是 Web、权限、事务和任务状态，TypeScript 可以共享类型并配合 Zod 做运行时校验，适合这一实现范围。

如果需要训练、复杂文档解析或已有 Python 算法生态，可以用独立服务接入。语言选择不会自动解决 Agent 可靠性；当前也要正视同步数据库和 scrypt 对 Node 事件循环的影响。

## 十、现场故障题演练

以下回答使用“先查证据 → 再控制影响 → 最后改进”的顺序。

| 面试官给出的场景 | 应回答的排查与处理重点 |
| --- | --- |
| 模型把 1000 件读成 10000 件 | 查原文、抽取结果和字段证据；当前存在性校验不充分，需补语义标注与歧义转人工；已产生草稿需撤销或重新审批，不能直接修改获批金额 |
| 一段消息同时询两种产品 | 当前单产品模型不足，要求拆分或人工处理；后续设计 quote/quote_lines，逐行证据、金额和审批，不声称已支持 |
| Worker 创建草稿后崩溃 | 检查租约、任务状态与 Run；重新执行复用 run 唯一报价，再恢复审批；验证中间状态，不能只重置所有任务 |
| 两名财务同时点击批准 | SQLite 写事务串行化，后执行者看到审批非 pending 后返回冲突；不能依赖按钮禁用 |
| 审批通过后产品成本上涨 | 当前政策版本检查不足以自动捕获产品变更；需要产品版本/快照及重新审批规则 |
| 飞书请求超时，但群里实际收到 | 标记 uncertain，由人工核对；不因超时自动重发造成重复通知 |
| 飞书返回限频错误 | 当前有限重试和分钟级退避；进一步按错误分类、供应商返回信息和全局发送速率控制，需实测 |
| 数据库坏了为什么飞书也没告警 | 当前告警投递依赖 API 与数据库；补独立外部告警接收器和第二通道 |
| 登录流量增大，接口全部变慢 | 查事件循环延迟、同步 scrypt 和数据库锁；做限流、异步密码计算及容量测试 |
| 销售离职后，排队任务还在执行 | 入口停用不等于异步任务撤销；补执行时授权检查及明确取消/转交策略 |
| 恢复脚本通过，但业务仍不能登录 | 结构完整不代表功能恢复；核对版本、配置和密钥，在隔离环境启动恢复库并走业务链路 |
| 压测全部返回 202，但积压越来越多 | 202 只代表接收，测完成速率与排队年龄；控制入口速率、消除瓶颈，必要时扩展消费架构 |
